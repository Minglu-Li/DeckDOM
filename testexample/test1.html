1. GC 四大核心基础问题

学习GC先理清四层逻辑

  1. 垃圾存在哪里？Java堆为主，元空间存放类元数据
  2. 什么是垃圾？GC Roots不可访问的对象
  3. 用什么回收？标记清除 / 标记复制 / 标记整理算法
  4. 谁执行回收？Serial / Parallel / G1 / ZGC收集器
核心区分：算法是理论，收集器是落地实现

2. Java 堆分代内存结构

Java Heap
├─ 年轻代 Young
│  ├ Eden：所有新对象默认分配
│  ├ Survivor From
│  └ Survivor To
└─ 老年代 Old：长期存活对象
  • 同一时间仅一个Survivor可用，GC后互换角色
  • JDK8 永久代废除，替换为元空间Metaspace（本地内存）
  • G1收集器：堆切割为均等Region，逻辑分代、物理不连续

3. Java 对象完整生命周期

new对象 → TLAB无锁分配至Eden
Eden空间不足 → 触发Young GC
存活对象移入Survivor，年龄+1
达到晋升阈值 / Survivor空间不足 → 晋升老年代
老年代GC标记不可达 → 释放内存
  • 超大数组：G1直接分配Humongous大对象区
  • 逃逸分析：局部小对象可栈上分配，不占用堆内存

4. 四类GC回收范围区分

GC类型 回收范围 核心特征
Young GC 全部年轻代 频率高、停顿短
Mixed GC G1专属 年轻代+高垃圾老年代Region
Major GC 仅老年代 语义模糊，工程不推荐使用
Full GC 整个堆+元空间 停顿极长，线上必须规避

5. JVM 如何判定垃圾对象

方案1：引用计数（已废弃）

对象自带计数器，循环引用场景无法回收，HotSpot不采用

方案2：可达性分析（主流实现）

从GC Roots遍历引用链，无法到达的对象判定为垃圾

GC Roots 来源

  • 虚拟机栈局部变量、static静态常量
  • JNI本地引用、synchronized锁持有对象
  • 系统核心线程、类加载器内部引用
禁止使用finalize()：执行不可控、存在对象复活风险

6. 四级引用强度划分

引用类型 回收规则 业务场景
强引用 只要可达绝不回收 日常业务对象
软引用 SoftReference 内存耗尽OOM前清理 内存缓存
弱引用 WeakReference 下一次GC直接清除 WeakHashMap
虚引用 PhantomReference 仅提供回收通知 堆外内存释放

7. 三大垃圾回收算法

  • 标记-清除：不移动对象，产生大量内存碎片（CMS使用）
  • 标记-复制：复制存活对象，无碎片，适配年轻代（对象朝生夕死）
  • 标记-整理：压缩内存消除碎片，适合老年代Parallel Old
分代收集不是新算法，是根据对象生命周期组合优化的策略

8. STW / 并行 / 并发 概念区分

  • STW 暂停：GC关键阶段必须暂停所有业务线程，所有收集器都存在短时停顿
  • 并行 Parallel：多GC线程同时工作，业务全程暂停（Parallel GC）
  • 并发 Concurrent：GC线程与业务同时运行（G1/ZGC），会产生浮动垃圾

9. 主流收集器选型方案

收集器 设计目标 适用业务
Parallel GC 最大化吞吐量 批处理、大数据离线任务
G1 GC 吞吐与延迟平衡 绝大多数线上Web/RPC服务
ZGC 亚毫秒极低停顿 大堆、延迟敏感核心业务 
# G1推荐启动参数
-Xms4g -Xmx4g -XX:+UseG1GC -XX:MaxGCPauseMillis=200
# ZGC启用参数
-XX:+UseZGC

10. 线上GC故障排查工具

# 实时监控GC指标，每秒刷新
jstat -gcutil 进程PID 1000

# 导出堆快照，分析内存泄漏
jcmd PID GC.heap_dump /tmp/heap.hprof

# 查看当前JVM全部GC参数
jcmd PID VM.flags
内存泄漏判断标准：多次Full GC后，堆使用基线持续上涨

11. 面试高频易错点总结

  • obj=null 不会立刻回收对象，仅断开一条引用链
  • 对象不一定等到15岁才晋升，Survivor不足会提前晋升
  • G1/ZGC 并非无STW，只是停顿极短
  • Java存在GC，但依然会发生内存泄漏
  • System.gc() 仅为建议，不会强制Full GC
